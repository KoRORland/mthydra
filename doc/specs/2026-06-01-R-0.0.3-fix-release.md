# Spec R — 0.0.3 fix release (post-0.0.2 install + upgrade hardening)

Status: **Draft, awaiting operator review.**
Predecessor: `doc/specs/2026-05-31-Q-controller-upgrade.md` (the upgrade tool whose first prod run uncovered most of these).
Successors blocked on this: any future fleet-wide upgrade. The 0.0.1→0.0.2 manual run on 2026-05-31..06-01 hit seven distinct papercuts; until they're fixed, the *next* operator install will be just as painful, and `mthydra-ops upgrade` itself is not actually a safe one-command tool.

---

## 1. Purpose

The 0.0.1 → 0.0.2 manual upgrade on a real AWS EC2 controller uncovered a chain of bugs that are independently small but together render both the install path AND the upgrade path unusable without expert hand-holding. This spec consolidates the fixes into one release (0.0.3) so the next install + upgrade pass can be done by a normal operator following the quick-start, end-to-end, without ad-hoc debugging.

The bugs split into three categories:

1. **Silent data-plane failures** that the operator only finds when they manually attempt an action that the daemon was supposed to be doing all along (the credential bug — every backup since install has been silently failing; the region bug — same symptom, different cause).
2. **Install-and-forget gaps** where the quick-start documentation produces a host that *looks* installed but actually cannot perform its core function (broken IAM policy in the doc; missing install-time smoke test that would have caught it; no schema-migrate command and no auto-migration on upgrade).
3. **Operator-ergonomics papercuts** that turn a 60-second task into a 30-minute debug chain (raw Python tracebacks on PermissionError; root-shell umask leaking into `pip install -e .` via mthydra-ops upgrade; heartbeat emails with no version/host identification).

This spec is the irreducible "make the install + upgrade flow honest" pass. It does NOT add new features; every R-Task is a fix for something that's already broken.

Out of scope (deferred):
- Multi-host orchestration of upgrades (spec Q-D7 deferral stands).
- Schema-rollback (still structurally hard; pre-upgrade backup remains the recovery floor per Q-D4).
- A standalone "diagnose" subcommand that probes everything (R-D5's install-time backup smoke is the lighter version of this; a full diagnose is its own spec when there's operator pull).

## 2. Locked design decisions

All approved in conversation 2026-05-31 + 2026-06-01.

| ID | Decision | Rationale |
|---|---|---|
| R-D1 | **`secret_access_key` stored as `"keyid:secret"`; consumer splits on first `:`.** `_build_destination` in `cli.py` extracts the right-hand side as the actual secret and uses the left-hand side as `access_key_id` (overriding `cfg.backup.access_key_id`, which by install convention matches anyway). Tolerate the no-colon legacy form. | Storage format was already `keyid:secret` (init + rotate both write it that way), but the consumer was passing the whole string to boto3 as the secret. Result: every PutObject since install signed with the wrong HMAC key → silent `SignatureDoesNotMatch`. The split-on-consume fix is one line and matches what the storage convention already implies. |
| R-D2 | **Auto-derive AWS region from the endpoint URL.** Regex `^https?://s3\.([a-z0-9-]+)\.amazonaws\.com/?$` against `cfg.backup.endpoint`; if it matches, use the capture group as region. Precedence: `MTHYDRA_BACKUP_REGION` env (existing override) → derived → "us-east-1" fallback (B2 / MinIO ignore region). | Hardcoded `region_name="us-east-1"` silently miscomputes SigV4 for non-us-east-1 AWS buckets. aws-cli derives this from the endpoint; mthydra should too. No new config field — the endpoint URL already carries the region for AWS. |
| R-D3 | **Quick-start IAM policy: replace `s3:GetObjectRetention` with the COMPLIANCE-write set.** New required actions: `s3:PutObject`, `s3:PutObjectRetention`, `s3:PutObjectLegalHold`, `s3:GetObject`, plus bucket-level `s3:ListBucket` and `s3:GetBucketObjectLockConfiguration`. Drop `s3:GetBucketLocation` (unused by the controller). No `s3:DeleteObject` (Object Lock COMPLIANCE forbids deletion anyway). | The current quick-start policy as written cannot succeed at writing a backup — `s3:GetObjectRetention` is read-only. Every first-install operator who followed the doc has a host that cannot back up. The fix is a doc edit + a callout step that asks the operator to verify the first backup blob appears in the bucket. |
| R-D4 | **Graceful file-read errors in cli.py.** Wrap every `Path(...).read_text() / read_bytes()` on operator-supplied paths with `try/except OSError`; print `<cmd>: cannot read --<flag>: <e>` to stderr and return exit 2. | The pattern already exists at one site (`image-build`'s profile_json). Five others (`_read_recipient`, `rotate-provider-credential --credential-file`, `descriptor-verify --payload-file/--sig-file`, `data-exit-reality-keygen`, two evidence file readers) dump raw tracebacks. Operators reading "PermissionError: [Errno 13]" cannot tell from that what they did wrong; the friendly message says exactly which flag's file failed. |
| R-D5 | **Install-time backup smoke test.** `mthydra-ops install` runs a final `backup-now` after preflight succeeds and refuses to declare success if the backup fails. Same for `install-standby`. | Without this, R-D1+R-D2+R-D3 each fail silently for ~30 days until retention-violation alerts start firing. With it, the failure is loud and immediate in the install output — operators see "backup FAILED: <error>" while still SSH'd into the host, not on a Saturday email. |
| R-D6 | **Force `umask 022` in `_pip_install` (and any other subprocess pip call).** Use `preexec_fn=lambda: os.umask(0o022)` so the editable .pth and dist-info are world-readable regardless of the caller's umask. | Root operators sometimes set `umask 077` (e.g. when writing a credential file) and forget to reset it before continuing. The next `pip install -e` then creates files mode 600 root:root; the mthydra service user cannot read them → `ModuleNotFoundError` at the next restart. The fix is one line per subprocess call site. |
| R-D7 | **`mthydra-controller schema-migrate` subcommand + auto-trigger in `mthydra-ops upgrade`.** New subcommand opens the DB, calls `apply_schema()`, prints `db v{old} → v{new}` (or "already at v{N}"). `cmd_upgrade` invokes it post-pip-install, pre-service-restart, when `_schema_would_migrate` returned True AND `--allow-schema-migration` was passed. | `apply_schema()` already walks all migrate_vN_to_vN+1 functions correctly; it's only ever called by fresh `init` or by standby `promote`. Existing-DB upgrades have no path to run it. Spec Q's `--allow-schema-migration` flag therefore gates the upgrade but never *runs* the migration — the flag is broken-by-design. The fix is two parts: expose `apply_schema` as a CLI command, and have the upgrade tool call it. |
| R-D8 | **Enrich heartbeat with version + hostname + schema version + git SHA.** Subject becomes `mthydra heartbeat @ {now} — {hostname} v{version}`. Body prepends `version: {version}\nhostname: {hostname}\nschema: v{schema_version}\nHEAD: {head_sha[:12]}\n\n` before the existing `summary_line`. | After a fleet-wide upgrade, operators reading heartbeat emails today have no way to tell which version a controller is actually running — silence in the heartbeat then tells you nothing about which version went silent. All four fields are cheap to collect (importlib.metadata, os.uname, one SELECT, one git rev-parse) and turn the heartbeat into a useful identification + drift-detection signal. |

## 3. Components changed (no new top-level modules)

### 3.1 `src/mthydra/controller/backup/s3_dest.py` — no changes
Consumer of credentials, not parser. Region still passed in by caller (R-D2 changes the caller).

### 3.2 `src/mthydra/controller/cli.py` — five edits

- `_build_destination` (line ~1422): split secret on `:`; derive region from endpoint when not overridden (R-D1 + R-D2).
- `_cmd_obs_heartbeat_now` (line ~1032) and the `ObsHeartbeatPublisher` constructor it builds: pass version/hostname/schema/SHA in (R-D8).
- `rotate-provider-credential` (line ~872): wrap the `Path(args.credential_file).read_text()` in try/except OSError (R-D4).
- `descriptor-verify` (line ~1185), `data-exit-reality-keygen` (line ~2781), two evidence readers (lines ~3313, 3384), `_read_recipient` (line ~37): same try/except wrap (R-D4).
- New `schema-migrate` subcommand handler (R-D7): opens DB via `connect`, calls `apply_schema`, prints version transition.

### 3.3 `src/mthydra/controller/observability/heartbeat.py` — constructor + run_once edit

Add `version`, `hostname`, `schema_version`, `head_sha` parameters to `ObsHeartbeatPublisher.__init__`. `run_once` composes the new subject + body (R-D8). Tests monkeypatch via constructor injection (no module-level globals).

### 3.4 `src/mthydra/ops/upgrade.py` — two edits

- `_pip_install`: add `preexec_fn=lambda: os.umask(0o022)` to subprocess.run (R-D6).
- `cmd_upgrade`: after `_pip_install` succeeds and before `_stop_service`, if `_schema_would_migrate` returned True AND `args.allow_schema_migration`, run `_controller_bin() schema-migrate --db-path <db>`. On failure, error out before touching the service (R-D7).

### 3.5 `src/mthydra/ops/install.py` — one edit per install command

`cmd_install` and `cmd_install_standby`: after preflight returns 0, invoke `_run_controller("backup-now", "--db-path", ..., "--config", ..., "--reason", "install-validation")`. On failure, print the same diagnostic-style hints (R-D2/R-D3 hints) and return non-zero (R-D5).

### 3.6 `doc/quickstart-mvp.md` — two edits

- Replace the IAM policy JSON block at lines 73-90 with the COMPLIANCE-write set (R-D3).
- After the install step that runs `mthydra-ops install`, add a callout: "Verify gen-0000000001.age appears in your S3 bucket. If `install` reports `backup FAILED: AccessDenied`, recheck the IAM policy in step 5 — `s3:PutObjectRetention` must be in the action list." (R-D5 surface.)

## 4. CLI surface — one new subcommand

```bash
mthydra-controller schema-migrate --db-path /var/lib/mthydra/state.sqlite
```

Output on a DB at v14 with code at v15: `schema-migrate: db v14 → v15 OK`.
Output on a DB already at the target: `schema-migrate: already at v15`.
Exit codes: 0 on success or no-op; 2 on DB-open failure; 3 on migration exception (operator must investigate; this is the irreversibility boundary).

No new flags on `mthydra-ops upgrade` — `--allow-schema-migration` already exists from spec Q. The behavior change is that the flag now actually does what the help says (R-D7).

Each R-Task is one PR-sized commit, followed by `git push origin main` per the working agreement.

- **R-Task 1** (R-D1): `_build_destination` keyid:secret split + regression test.
- **R-Task 2** (R-D2): region auto-derive + tests for endpoint variants (AWS regional, B2, MinIO localhost).
- **R-Task 3** (R-D3): quickstart IAM policy fix + callout step. (Doc-only; smoke-tested by R-Task 5.)
- **R-Task 4** (R-D4): graceful OSError wrap on the six read_text/read_bytes sites + per-site tests.
- **R-Task 5** (R-D5): install-time backup-now + install.py tests with monkeypatched run_controller.
- **R-Task 6** (R-D6): umask 022 in `_pip_install` + regression test (assert preexec_fn is set).
- **R-Task 7** (R-D7): `schema-migrate` subcommand + cmd_upgrade integration + two tests (subcommand standalone; cmd_upgrade invokes it when gated).

After R-Task 8 lands, bump `pyproject.toml` to 0.0.3, tag `v0.0.3`, push tag. The user's next prod step is `mthydra-ops upgrade` on the 0.0.2 host — which validates the upgrade tool a second time, this time on a release where the upgrade tool itself is the thing being fixed.

## 6. What we are deliberately NOT changing

- **Storage format of provider credentials** stays `keyid:secret`. R-D1 fixes the consumer, not the format — changing the format would require a one-time DB migration and break standby promotion. The split-on-consume approach is one line and equivalent.
- **`MTHYDRA_BACKUP_REGION` env var** stays the top-priority override (R-D2). The env var was always the intended escape hatch; we just gave it a sensible default derivation when it's unset.
- **`apply_schema()`'s migration walker** stays as-is. R-D7 only exposes it as a CLI command — the implementation has been tested by every fresh init since v1.
- **Auto-rollback behavior in spec Q** stays untouched. R-D7 sequences the schema migration BEFORE the service restart, so if the migration fails, no rollback is needed (the upgrade aborts before touching the service). If the *post-migration* verify fails, auto-rollback runs as designed — the DB is then forward-migrated against old code, which is the exact failure mode Q-D6 warned the operator about and Q-D4 made restorable via pre-upgrade backup.
